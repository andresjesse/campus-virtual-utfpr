# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Campus Virtual V2 (UTFPR TCC): a rewrite of a 3D virtual campus plus an admin panel that manages its content. Monorepo:

- `frontend/` — React 19 + TypeScript + Vite + Mantine 9 + React Router 7. Two halves: the public **virtual map** on `/` (Three.js, see **Virtual map** below) and the **admin panel** (`/admin/*`) that manages its content.
- `backend/` — PocketBase (no source code, just `pb_migrations/` and `pb_hooks/`). PocketBase is the whole API; the frontend talks to it directly through the `pocketbase` SDK.

UI strings, PocketBase error messages and hook messages are in Brazilian Portuguese. Keep new user-facing text in pt-BR. Frontend UI text lives in `frontend/src/constants/messages.json` (see **UI strings** below).

## Commands

Run everything from `frontend/` with **yarn** (CI uses Node 24 and `yarn install --frozen-lockfile`).

```bash
yarn dev                  # Vite on :3000 (strictPort — fails if 3000 is taken)
yarn build                # tsc -b && vite build
yarn lint                 # eslint .
yarn test                 # Jest (unit + integration)
yarn test tests/unit/logic/admin-permissions.test.ts   # single file
yarn test -t "name fragment"                            # single test by name
yarn test:e2e             # Playwright (chromium only; auto-starts `yarn dev` on 127.0.0.1:3000)
```

CI (`.github/workflows/ci.yml`, PRs to `main`/`development`) runs lint → `test:ci` and Playwright, all from `frontend/`.

Full stack (from repo root): `docker compose up` → app on `:3000`, PocketBase on `:8080` (admin UI at `/_/`). First time: `cp frontend/.env.example frontend/.env`. The frontend container runs `yarn && yarn dev` against the bind-mounted `frontend/`; `backend/pb_data/` is the (gitignored) database.

## Backend / database

- The PocketBase container runs with `--automigrate=0`, so schema edits made in the PocketBase admin UI do **not** generate migration files. Persist schema changes yourself: either a fresh `*_collections_snapshot.js` (`./pocketbase migrate collections` inside the container) or a small hand-written `migrate(up, down)` like `pb_migrations/1789002723_add_mesh_name_unique_index.js`. Migrations run on startup; if they don't, `./pocketbase migrate up` in `/pb`.
- Collections: `users` (auth; has `is_admin`, `department`), `content_page`, `file_block`, `rtf_block`, `diagram_block`, `menu_items`, `menu_categories`, `entities`, `mesh`. Access rules live in the migrations (e.g. `mesh` and `entities` writes require `@request.auth.is_admin = true`; block/page writes require any authenticated user). `mesh` and `entities` are publicly listable/viewable and `mesh.file` is not `protected` (`1791245475_allow_public_virtual_map_read.js`), because logged-out visitors load the map; that also exposes inactive entities through the API, which the frontend filters out (`listActiveEntities`).
- `pb_hooks/content_page_relation.pb.js` enforces the invariant that a `content_page` is linked to **either** an `entities` record (`content_page.entity`) **or** a `menu_items` record (`menu_items.page`), never both, and a page maps to at most one menu item. The frontend service mirrors this (see below); keep both sides consistent when touching either.
- `pb_hooks/menu_item_nesting.pb.js` enforces that a nested `menu_items` record shares its parent's `category`, and propagates a category change down the whole nested subtree. Unlike the hook above it uses the **model** hooks (`onRecordCreate`/`onRecordUpdate`), so it also covers writes that don't come from the API, such as the PocketBase dashboard. Two constraints learned the hard way: a handler runs in its own context and **cannot call file-scope helpers** (doing so 400s every write), and anything after `event.next()` runs post-commit, so the cascade is deliberately not atomic with the record's own update.
- The three block collections share one `position` sequence per page (`1793000000_add_block_position.js` adds the optional integer field and backfills existing blocks by `created`). `pb_hooks/content_block_position.pb.js` (model `onRecordCreate`) appends a new block after the page's highest `position` across all three collections. A number field can't tell "not sent" from `0`, so a `0` on create is treated as "not set"; set an explicit order by updating `position` after creation. Deleting a block leaves a gap, which is fine because only the relative order matters.
- Known gap: nesting cycles are only prevented in the frontend (`getMenuItemParentOptions`); a direct API call can still point two items at each other, which would make the cascade recurse until the stack blows.

## Frontend architecture

Path alias `@/` → `frontend/src/` (Vite, tsconfig and Jest all configured). Source files commonly import with explicit `.ts`/`.tsx` extensions.

**Provider/route stack.** `main.tsx` → `MantineProvider` (dark default, `theme.ts`) → `ProvidersGroup` (`AuthenticationProvider` → `DialogProvider`) → `Router` (`router.tsx`). Routes are nested: `ProtectedRoute` (requires login) → `/admin` `AdminLayout` → `AuthorizationRoute capability="…"` → page. Pages are exposed through the `Pages` object (`pages/index.ts`, `pages/admin/index.ts`), which is what `router.tsx` consumes — add new pages there.

**Authorization is frontend UX, not security.** `helpers/authorization/admin-permissions.ts` maps `user.is_admin` to capabilities (`pages.manage`, `menu.manage` for editors; plus `entities.manage`, `meshes.manage` for admins). The real enforcement is the PocketBase collection rules in the migrations; keep the two in sync when adding a capability.

**Data layer.** All PocketBase access goes through `services/` (`content-page-service.ts`, `mesh-service.ts`) using the single client in `services/pocketbase.ts`; components/hooks never call the SDK directly (auth provider excepted). Calls pass `requestKey: null` to avoid PocketBase's auto-cancellation of concurrent identical requests. Error text is normalized by `helpers/request-error-helper.ts`: `getRequestErrorKind` classifies a failure once (`duplicate`, `serverMessage` for pt-BR `pb_hooks` text shown verbatim, the HTTP statuses, `network`, `generic`), `getRequestErrorMessage(error, domainMessages?)` resolves it against `messages.errors` or an optional per-domain `errors` subtree whose keys are kind names (e.g. `messages.mesh.errors.duplicate`), and `getRequestFieldErrors` returns PocketBase's per-field errors so a form can show one under the field that caused it. Add a new failure state by adding a kind plus a `messages.errors` key — never by branching at the call site.

**Content pages and blocks** (the core feature):
- A page's body is a list of blocks, each stored in its own collection: `rtf_block`, `file_block`, `diagram_block` (`PAGE_BLOCK_COLLECTIONS` in `constants/content-constants.ts`; `ContentPageBlocksEnum` is derived from it). Blocks reference the page via `page`.
- Rendering is registry-driven: `content-input/content-blocks/registry.ts` (display body) and `…/overlay/registry.ts` (editor) each map block type → component. **Adding a block type** means: extend `PAGE_BLOCK_COLLECTIONS`, add a PocketBase collection + migration, add both registry entries, add its `get…BlocksMetadata` in the service, and handle it in `prepareRecordToSave` / `getBlockContent` if its content isn't plain JSON/text.
- `useContentBlockData` loads and upserts one block's content. Block `content` is a union (`ContentPageBlockValue`): string for RTF, and for file blocks an object `{ newFiles, deletedUrls, urls }` that `upsertBlockContent` translates into PocketBase's `content+` / `content-` file-field operators.
- RTF content is sanitized (`helpers/sanitize-rich-text.ts`, DOMPurify) before saving.
- **Block order** follows the shared `position` field (see **Backend / database**). `helpers/content-block-order-helper.ts` is the pure layer: `flattenBlocksMetadata` merges the per-collection metadata into one list sorted by `position` (blocks without one go last), and both the editor (`BlocksList`) and the virtual map modal use it. `moveBlock`/`getDropIndex`/`getDropSlot` compute a move, and `reorderBlocks` in the service writes only the blocks whose `position` changed (`getBlockPositionChanges`). `prepareRecordToSave` strips `position`, so saving a block's content never moves it. `BlocksList` reorders optimistically and refetches the stored order if the write fails; a block is moved with the up/down buttons (`BlockMoveButtons`, passed through `BlockDisplay`'s `actions` slot) or dragged by its handle (`SortableBlockItem`). The drag is only enabled while the handle is pressed, so text inside a block stays selectable. Reorder drags carry `BLOCK_REORDER_DATA_TYPE` and palette drags carry `text/plain`; `DraggableContainer`/`DroppableContainer` take the type as a prop and ignore drags of other types, so dropping a block never opens the new-block overlay. `BlocksList` owns one `dropSlot` (`0..n`) for the whole list, so only one insertion line shows at a time; the line has `pointer-events: none` because otherwise it would catch the pointer and flicker. Native HTML5 drag and drop doesn't fire on most touch browsers, so the handle is hidden on `(pointer: coarse)` (blocks are reordered with the up/down buttons there), and a palette card (`ElementPreviewCard`) also adds its block on click/Enter/Space: `ElementPalette` dispatches `CONTENT_EDITOR_EVENTS.BLOCK_ADD_REQUESTED` on `contentEditorEventBus` (`helpers/content-editor-event-bus.ts`, built on `createEventBus`), and `BlocksList` handles it exactly like a drop. The palette and the list sit in different branches of the editor page, which is why they talk through the bus instead of props.
- Page metadata (title + relation) **autosaves** via `use-content-page-autosave.ts` (debounced by `AUTOSAVE_DELAY`, serialized through a promise queue; a new page is created on first valid save and the route is switched to its id). Blocks, in contrast, are saved explicitly from the edit overlay, and only once the page has a title and relation.
- The page↔entity/menu-item relation is one form value encoded as a `"type:id"` string (`encodeRelation`/`parseRelation` in `helpers/content-pages-service-helper.ts`). `updateContentPage` / `createContentPage` handle the two-collection write (unlinking stale menu items); `deleteContentPage` manually cascades through all block collections.

**Record list pages.** `ContentPageListPage`, `MeshListPage`, `EntityListPage`, `MenuCategoryListPage` and `MenuItemListPage` get all their data logic from `hooks/use-record-list.ts`: records, loading, error, `reload`, the locale search (`query`/`setQuery`/`filtered`, via `use-locale-search.ts`) and the confirm → delete → notify cycle (`deletingId`/`requestDelete`, through `DialogContext`). A page only supplies its service functions, a `getSearchableText`/`getName` accessor and its `messages.<domain>.list` subtree, then renders its own JSX; the search field and "new" button header is the shared `components/table/RecordListToolbar.tsx`. The hook requires the delete-flow keys to be named the same in every domain (`deleteConfirmTitle`, `deleteConfirmFirst` with `{name}`, `deleteConfirmSecond`, `deletedTitle`, `deletedMessage`; the error title comes from `common.deleteErrorTitle`), so mirror `mesh.list` when adding a new list area.

**Meshes** (`components/mesh/`, `pages/admin/meshes/`, `services/mesh-service.ts`): admin-only CRUD for uploaded `.glb` models (`constants/mesh-constants.ts` sets MIME type and 5 MB limit, matching PocketBase's default file-field size); `mesh.name` has a unique index.

**Entities** (`components/entity/`, `pages/admin/entities/`, `services/entity-service.ts`): admin-only CRUD for the `entities` records that place a mesh in the virtual map — `slug` (unique index), a required `mesh` relation, `is_active`, and nine transform numbers (`pos_x` … `scale_z`). PocketBase treats a `required` number as "nonzero", so `pos_*`/`rotation_*` are optional in the schema (`1792540800_allow_zero_entity_position_rotation.js`) to accept `0`, and only the form requires them to be filled in; `scale_*` stays `required` and rejects `0`. `constants/entity-constants.ts` holds the collection name, the transform groups/axes that drive both the validator and the form grid, and the 0/0/0 · 0/0/0 · 1/1/1 defaults. `helpers/entity-service-helper.ts` owns slug validation and the pure `validateEntityForm`; the service owns trimming and string→number coercion (`toEntityPayload`). Form values deliberately use flat PocketBase-identical field names, because a later issue adds a JSON bulk-edit view over the same object. Transform inputs keep Mantine's raw `number | string` while typing — coercing on change would make a field impossible to clear or to type `-`/`1.` into. Rotations are in **degrees** (converted when placed in the scene).

**Virtual map** (`components/virtual-map/`, `hooks/use-virtual-map.ts`, `helpers/virtual-map-scene-helper.ts`, `constants/virtual-map-constants.ts`): the public 3D view on `/`, plain `three` (no react-three-fiber). `createVirtualMapScene` builds the renderer, camera, lights and `OrbitControls`; camera clipping planes, orbit limits, the pan bounds that `clampControlsTarget` enforces, and lighting/shadow values are fixed constants in `VIRTUAL_MAP_*`, scene colors come from `branding.colors.scene`. `createVirtualMapScene(canvas, { shadowsEnabled, pixelRatio })` takes the visitor's graphics settings (see **Graphics settings**). The shadow map is **static**: `renderer.shadowMap.autoUpdate` is `false`, and `useVirtualMap` sets `shadowMap.needsUpdate = true` once, after every entity is placed. Nothing in the scene moves after loading, and the hover highlight only swaps the visible materials, so no other shadow pass is needed; anything that later changes the scene content or the light must request one again. `useVirtualMap(canvasRef)` owns the whole lifecycle inside one effect: render loop (`setAnimationLoop`), resize, `listActiveEntities` → `groupEntitiesByMesh` (each `.glb` downloads once and is `clone()`d per entity) → `loadModels` (`GLTFLoader`, combined percentage) → `applyEntityTransform`; a failed model is skipped with a warning notification, a failed listing sets `status: "error"` with `retry`. Three.js objects live in that effect's closure and **never in React state** — React only holds `status`/`progress`/`error`. On unmount the effect stops the loop, disposes the controls, runs `disposeObject3D(scene)` (frees geometries, materials and their textures once each) and calls `renderer.dispose()` + `forceContextLoss()`; anything added to the scene must be reachable from it, or it leaks GPU memory. Home **lazy-loads** `VirtualMapViewer` (`lazy` + `Suspense` with the loading overlay, inside the generic `ErrorBoundary` that shows `VirtualMapErrorOverlay` when the chunk can't download or the renderer throws), which keeps `three` out of the main bundle; a static import of `three`, `three/addons/*`, `use-virtual-map` or `virtual-map-scene-helper` from anywhere else silently pulls it back in, so keep them behind `VirtualMapViewer`. Only entities that have a `content_page` are **pickable**: `listEntityIdsWithPage()` is loaded in parallel with `listActiveEntities`, and an entity outside that set (the base environment, props such as trees) is still placed in the scene but is never marked with `setPickableEntity` or added to the pickable list, so it can't be hovered, highlighted or clicked. A page with no blocks still counts. The **hover highlight** tints the hovered entity with an emissive color (`branding.colors.scene.entityHighlight`, `VIRTUAL_MAP_HIGHLIGHT.emissiveIntensity`) through `applyEntityHighlight`, which gives only that instance cloned materials (`model.clone()` shares materials between instances of a mesh, so tinting in place would light up all of them) and returns a `restore()` that puts the originals back and disposes the clones. The raycast (`pickEntityRoot`) runs at most once per animation frame on the latest pointer position, only for mouse pointers with no button held; a button press, `pointerleave` and unmount all clear the hover, and the canvas cursor is `pointer` while an entity is hovered.

**Virtual map event bus** (`helpers/event-bus.ts`, `helpers/virtual-map-event-bus.ts`, `types/event-bus.ts`, `types/virtual-map-events.ts`): React and the scene never import each other; they talk through the `virtualMapEventBus` singleton, built by the generic, dependency-free `createEventBus<Events>()` (`register` returns its own unregister function, for `useEffect` cleanup; `dispatch` takes no payload argument for an event typed `undefined`). Event names live in `VIRTUAL_MAP_EVENTS` (UPPER_SNAKE keys and values) and payloads in the `VirtualMapEvents` type, which is keyed by those constants — a new event goes in both, and always through the constant, never a string literal. Today the scene dispatches `ENTITY_SELECTED` (`{ id, slug }`) when a click hits an entity, `SELECTION_CLEARED` when it hits nothing, and `RENDER_STATS_UPDATED` (`{ fps }`) once per `VIRTUAL_MAP_STATS_SAMPLE_MS`, from the frames the render loop actually draws (`createFrameRateSampler` in `helpers/virtual-map-render-stats-helper.ts`). A press whose pointer ever moves more than `VIRTUAL_MAP_POINTER.clickTolerance` from where it went down is an orbit drag and selects nothing, even if it is released back at the start, and `pickEntity` walks up from the hit mesh to the root that `setPickableEntity` marked. The React side (`useVirtualMapSelection`) holds only the selection, and closes by *dispatching* `SELECTION_CLEARED` rather than clearing its state directly, so scene-side listeners get the same event. `useVirtualMapEntityPage(selected)` reacts to the selection: it fetches the `content_page` linked to the entity (`getContentPageByEntity`) and its block metadata, and returns `status` (`none` / `loading` / `ready` / `error`), `page`, `blocks` and `retry`. `VirtualMapViewer` opens `VirtualMapEntityModal` (a centered Mantine `Modal`; ✕, Esc and an outside click all call `clearSelection`) once the status is `ready`/`error`, or `loading` for longer than `VIRTUAL_MAP_ENTITY_LOADING_DELAY_MS` (`useDelayedFlag`), so an entity without a page opens nothing instead of flashing the modal. Each block is a read-only `VirtualMapBlock` (`useContentBlockData` + `BLOCK_DISPLAY_BODY`, never `BlockDisplay`, whose header has the edit/delete actions). New React↔scene communication must go through this bus. Neither the bus nor the selection hook imports `three`, which keeps them safe to use outside the lazy boundary.

**Virtual map deep links** (`hooks/use-virtual-map-deep-link.ts`): `/map/:slug` renders the same `Home` as `/` (React keeps it mounted when switching between them, so the scene is not rebuilt), and bare `/map` redirects to `/`. `useVirtualMapDeepLink(isMapReady, selectedSlug)` is called from `VirtualMapViewer`, **inside** the lazy chunk, because the bus doesn't replay events and `useVirtualMapSelection` only listens once that chunk has loaded — a dispatch from `Home` could be lost. Once the map status is `ready` it resolves the slug verbatim with `getActiveEntityBySlug` plus `getContentPageByEntity` and dispatches `ENTITY_SELECTED`; an unknown, inactive or page-less slug shows a warning and replaces the URL with `/`, a failed request shows an error and keeps the URL. The URL follows the selection both ways: `ENTITY_SELECTED` pushes `/map/:slug` and `SELECTION_CLEARED` pushes `/`, and a URL change from history clears or re-resolves the selection. React Router applies `navigate()` in a later render than the selection it follows, so the URL→selection effects depend on `slug` only and read the selection through `useEffectEvent`; making them depend on the selection clears it right after every click. The hook returns the URL `slug`, and `VirtualMapViewer` keeps `VirtualMapTour` disabled while one is present: the selection only arrives after the lookup requests, so gating on it would let the tour flash open first. Disabling only pauses the tour (it is marked completed on close/finish), so a new visitor arriving through a link sees it once the modal closes.

**Onboarding tour** (`components/virtual-map/virtual-map-tour/`, `hooks/use-virtual-map-tour.ts`, `helpers/virtual-map-tour-helper.ts`, `constants/virtual-map-tour-constants.ts`): a first-visit walkthrough built on Mantine (no tour library). `VIRTUAL_MAP_TOUR_STEPS` lists the steps, and `VIRTUAL_MAP_TOUR_STEP_TARGETS` maps each one to a `data-tour` value from `VIRTUAL_MAP_TOUR_TARGETS` (or `null` for a centered step). To point a step at an element, put `data-tour={VIRTUAL_MAP_TOUR_TARGETS.…}` on it, and never select it by class or aria label. The copy is in `messages.virtualMap.tour.steps.<step>`, and a step may add a `touchBody` that is shown on `(pointer: coarse)`. `useVirtualMapTour(enabled)` reads the seen flag (`getStorageKey("virtual-map-tour-completed")`) once on mount. `VirtualMapViewer` passes `status === "ready"`, so the tour never covers the loading overlay. `close` is the only way out: Pular, Esc, Concluir on the last step and **any press outside the card** all call it, and it saves the flag. The storage helpers swallow `localStorage` errors, so with blocked storage the tour simply shows on every visit. `VirtualMapTourMask` is one SVG path drawn with `fill-rule="evenodd"`: the dimmed area blocks the map, and the rounded hole around the target lets pointer events through. A target that fills the viewport (the canvas) gets no hole (`getTourSpotlight` returns `null`), and its card is centered. The card (`VirtualMapTourCard`) is a focus-trapped `role="dialog"`, and its ref must go through `FocusTrap`'s `innerRef`, because `FocusTrap` replaces its child's `ref` and the outside-press check would otherwise treat every press as outside. `restartTour()` clears the flag and reloads the page, and the top-left toolbar's help button calls it. Specs and component tests that render a `ready` map must set the flag first (`skipVirtualMapTour` in `tests/e2e/`, `localStorage.setItem` in Jest), or the mask blocks their clicks.

**Map toolbar** (`components/virtual-map/virtual-map-toolbar/`): `VirtualMapToolbar` is the generic floating panel. `position` is a `VirtualMapToolbarPosition` (`top-left` / `top-right` / `bottom-left` / `bottom-right`), and the panel stacks its children vertically with a divider between each. Pass the buttons as direct children, because a fragment counts as a single child and gets no dividers. `VirtualMapToolbarButton` takes a Phosphor `icon` component (not a name), a `label` (used as both tooltip and aria label) and `onClick`. Each corner's content lives in its own component, such as `VirtualMapTopLeftToolbar`, which `VirtualMapViewer` renders once the map is ready. Add a new map control there, not inline in the viewer.

**Graphics settings** (`components/virtual-map/virtual-map-graphics/`, `hooks/use-virtual-map-graphics-settings.ts`, `helpers/virtual-map-graphics-helper.ts`, `constants/virtual-map-graphics-constants.ts`, `types/virtual-map-graphics.ts`): visitor-facing options for low-end devices. `VirtualMapGraphicsSettings` holds `shadowsEnabled`, `pixelDensity` (`auto` / `low` / `medium` / `high`, ratios in `VIRTUAL_MAP_PIXEL_DENSITY_RATIOS`) and `fpsCounterVisible`, stored as JSON under `getStorageKey("virtual-map-graphics")`. `loadGraphicsSettings` swallows storage errors and fills an invalid or partial value from `VIRTUAL_MAP_GRAPHICS_DEFAULTS`. `resolvePixelRatio(density, device)` never goes above the device's ratio or `VIRTUAL_MAP_MAX_PIXEL_RATIO`; `auto` picks `low` on a device that looks low-end (`VIRTUAL_MAP_LOW_END_DEVICE`: few cores, or little `navigator.deviceMemory` where the browser reports it), `medium` on other `(pointer: coarse)` devices and `high` elsewhere. `readDeviceInfo()` is the only place that reads the browser values, which keeps the rest testable. The settings are read **once**, when the scene is created, and never applied at runtime: the menu (`VirtualMapGraphicsSettingsButton`, a `Popover` above the help button in `VirtualMapTopLeftToolbar`, and the target of the tour's `graphics` step) edits a draft, and save calls `applyGraphicsSettings`, which stores it and reloads the page; closing the menu discards the draft. The "Atual: …" line shows `currentPixelDensity`, the level (`low` / `medium` / `high`) of the **stored** density on this device, so `auto` shows the level it picked. `VirtualMapFpsCounter` (top-right, `pointer-events: none`) is rendered by `VirtualMapViewer` only when `fpsCounterVisible` is on, and shows only the latest FPS. On screens narrower than the `xs` breakpoint the menu opens below the toolbar instead of to its right, its width is capped to the viewport, and Floating UI's `size` middleware caps its height so it scrolls instead of going off screen.

**Menu** (`components/menu/`, `pages/admin/menu/`, `services/menu-category-service.ts`, `services/menu-item-service.ts`): editor-reachable CRUD for the navigation overlay, split across two tabs driven by `RouteTabs` + `MENU_TAB_OPTIONS` (`helpers/menu-tabs-helper.ts`). **Categories** are label-only (unique index on `label`); deleting one cascades to its items in PocketBase. **Items** carry `label`, a required `icon` upload, a required `category`, an optional self-relation `parent` (cascade-deleted with its parent) and exactly one target — either `href` or a `page` relation — chosen with a `SegmentedChoice` and cleared on the unused side by `toMenuItemPayload`. `helpers/menu-item-service-helper.ts` owns the pure layer: `validateMenuItemForm`, `toMenuItemFormValues`, `buildMenuItemPageOptions` (marks each content page available / held by another item / held by a 3D entity, the last `disabled`) and `getMenuItemParentOptions` (returns nothing until a category is picked, then filters to that category and walks each candidate's parent chain, so an item can't be nested under its own descendant or across categories). Changing the category clears an already-chosen parent, and the same rule is enforced server-side by `pb_hooks/menu_item_nesting.pb.js` — keep the two in sync. `listMenuItems` groups the list by the expanded category label (`sortMenuItemsByCategory`), because PocketBase can only sort a relation by id. Picking a page another item holds opens a `DialogContext.confirm` warning that the old link is only cut on save; the service then calls `unlinkMenuItems` before the write, because `pb_hooks/content_page_relation.pb.js` rejects a page claimed twice. That transfer can leave the previous item with no target at all — a state the form itself forbids — so the list flags those rows in `feedback.warning` with an explanatory tooltip.

**One component per file.** Every React component lives in its own file (named after the component, default export), even small ones used by a single parent — don't define helper/sub-components beside the main one (e.g. `FileCard` is `components/file/FileCard.tsx`, not inline in `SingleFileDropzone`. Components used by one feature live in that feature's folder (`components/mesh/`, …); once a second feature needs the same control, lift it to a generic folder — `components/file/`, `components/segmented-choice/`, `components/tabs/`, `components/error-boundary/` — instead of copying it). Non-component helpers and types stay in `helpers/`/`types/`. Known gap: `DropzoneSection` still defines `DropzoneStatusIcon` inline; extract it when touching that file.

**Branding.** Colors, names and the localStorage namespace live in `src/config/branding.ts` (applied by `apply-branding.ts`); the `VITE_BRAND_*` values in `frontend/.env` (used by `index.html` meta tags/favicon and the pre-render body background in `main.tsx`) must be kept aligned with it. Use `getStorageKey()` for localStorage keys, and read/write them through `readStorageItem`/`writeStorageItem` (`helpers/storage-helper.ts`), which swallow the errors blocked storage throws (e.g. some private modes). Components must take colors from here (see **Styling**), never from raw hex values.

**Domain-agnostic naming.** The project is open source and meant to be reusable for any place that wants a navigable 3D map (a hospital, a company site…), so the code must not assume a university campus. "Campus" and "UTFPR" are this deployment's content, not the code's domain: they belong only in `branding.ts`, `.env`, `messages.json` and the database. Name the 3D viewer **virtual map** — `virtual-map-*` files (`constants/virtual-map-constants.ts`, `helpers/virtual-map-scene-helper.ts`), `VIRTUAL_MAP_*` constants, `VirtualMap*` components/types/hooks, a `virtualMap` messages domain — and pick equally neutral names (`map`, `scene`, `bounds`, `entity`) for anything new. Never put `campus`, `university` or `utfpr` in a file, identifier, folder or test description.

**UI strings.** `src/constants/messages.json` is a nested key-value catalog of all user-facing frontend text (pt-BR today), so another language can be supported later by swapping the file's content. Don't hardcode new user-facing text in components or helpers (including `aria-label`s, placeholders and notification titles/messages); add a key instead.
- Access: `import messages from "@/constants/messages.json"` and plain property access (`messages.mesh.list.title`). TypeScript infers the keys from the JSON, so a missing key is a compile error.
- Structure: domain → area → string. A domain may also have an `errors` area whose keys are `RequestErrorKind` names, picked up by `getRequestErrorMessage` (see **Data layer**). Current domains: `common` (generic strings reused across areas: `back`, `next`/`skip`/`finish` (the tour's step buttons), `retry`, `save`, `saving`/`saved`/`saveError`, `showMore`/`showLess`, `selectFiles`, `cancel`/`delete` for the confirm dialog, plus shared table/field strings `createdAt`, `updatedAt`, `actions` and the `emptyValue` dash placeholder), `block` (empty/file validation, `page.missingFields*`), `files` (`dropzone`, `rejection`), `errors` (HTTP/network cases used by `request-error-helper.ts` only — don't add unrelated strings here), `mesh` (`identifier`, `list`, `editor`), `entities` (`slug`, `transform`, `list`, `editor`), `menu` (`tabs`, shared by both menu tabs), `menuCategories` (`errors`, `label`, `list`, `editor`), `menuItems` (`label`, `link`, `list`, `editor` — deliberately no `errors` area, since nothing in that domain maps to a `RequestErrorKind`), `contentPages` (`editor`, `list`), `virtualMap` (`home`, `viewer`, `entityModal`, `menu`, `toolbar`, `graphics`, `fpsCounter`, `tour`), `login` (`form`, `validation`, `authentication`), `authentication` (`route`), `adminLayout`, `adminNavigation`, `notFound`, `palette`. Only keys of an `errors` area are checked against `RequestErrorKind`, so a failure text that isn't a request kind (e.g. `login.authentication.invalidCredentials`) goes in another area. Add a new top-level domain for a new area, and reuse existing keys instead of duplicating them — check `common` first (`ReturnButton`, `MeshEditorPage` and `ContentPageEditorPage` all reuse it) before adding a new one.
- Keys: camelCase at every level (domains included, e.g. `contentPages`), with suffixes such as `…Title`, `…Message`, `…Label`, `…Placeholder` on leaves.
- Interpolation: placeholders are written `{name}` inside the string (e.g. `mesh.list.editAriaLabel`) and substituted with `formatMessage` from `helpers/message-helper.ts` — don't hand-roll `.replace()` at call sites. Pass a bare string for a single-placeholder message (`formatMessage(messages.mesh.list.editAriaLabel, name)`; it fills every placeholder, so don't use it on a multi-placeholder string) and an object when the string has several (`formatMessage(template, { name, count })`, where unknown keys are left as `{key}`). Compute fallbacks in a variable above the JSX rather than inlining them in the argument.
- Tests should assert on `messages.…` values instead of copying literals (see `tests/unit/logic/content-block-validation.test.ts`).
- No runtime locale switching exists, and we deliberately **do not use an i18n library** (see **Dependencies**).

**Styling.** Mantine props first, then inline `style={{}}`, and CSS modules only when really needed (direction set in commit `af164a5`). Pick the first option that works:
1. Mantine component props (`variant`, `size`, `color`, `radius`, …) and Mantine style props (`bg`, `c`, `p`, `bd`, `w`, …). If the same look repeats across components, put it in `theme.ts` with `Component.extend({ defaultProps / styles })` instead of repeating it at call sites.
2. Inline `style={{ … }}` for small one-off tweaks Mantine props can't express (e.g. a genuinely dynamic value). The same color rule applies inside it.
3. A `*.module.css` file only when really needed (pseudo-selectors/states, keyframes, complex selectors or media queries that inline styles can't do). Don't create one for something props or inline styles can do. Older components still use `*.module.css`; migrate them opportunistically when touching them, don't rewrite them wholesale.
- **Colors come from `src/config/branding.ts`, never raw values.** No hex/`rgb()`/`hsl()` literals in `.tsx`, `.ts` or `.css`. In TSX use `branding.colors.*` (typed; e.g. `bg={branding.colors.surface.interactive}`), or the `var(--app-*)` CSS variables that `apply-branding.ts` publishes on `:root` (the only option inside `.module.css`, e.g. `var(--app-text-primary)`). The brand palette is also Mantine's `primaryColor` (`brand`), so `color="brand"` and Mantine's default primary already follow it. Derive shades with `color-mix()` on a token, not with a new literal.
- **Need a color that isn't a token?** Add it to the `Branding` type and value in `branding.ts` and to the `variables` map in `apply-branding.ts` (plus the `VITE_BRAND_*` value in `frontend/.env` if it's used before React renders); don't inline it. Use `feedback.*` for success/warning/error/info instead of Mantine's `blue-6`/`red-6`, etc.
- **Responsive layout uses Mantine's breakpoints only** (`xs` 36em, `sm` 48em, `md` 62em, `lg`, `xl`): responsive style props (`px={{ base: "md", sm: "2rem" }}`), `hiddenFrom`/`visibleFrom`, `useMediaQuery` built from `theme.breakpoints` (pass `getInitialValueInEffect: false` when the first render must already be right), and in CSS modules `@mixin smaller-than $mantine-breakpoint-xs` / `$mantine-breakpoint-*` (from `postcss-preset-mantine`). Never a raw pixel width. Phones in portrait are below `xs`, small tablets in portrait sit between `xs` and `sm`, and two-column admin layouts stack below `md`. Something that depends on touch rather than width (tap targets, the hidden drag handle, the larger root font on tablets in `globals.css`) uses `(pointer: coarse)`. Small `ActionIcon`s get a 44px touch target from `components/action/touch-action-icon.module.css` (`className={classes.action}`). Admin page heights subtract `var(--app-shell-header-offset)`, never a hardcoded header height.
- Known gaps: `PreviewImageCard` has a raw `rgba(0, 0, 0, 0.4)` shadow. Inline `style={{}}` is also still common (`PreviewImageCard`, `FilesPreviewSection`, `ReturnButton`, `PageTable`, `ContentPageForm`); move what Mantine props can express (e.g. `alignSelf`, widths) to props. Fix when touching those files.
- Design references (Figma export and PNGs) are in `design-reference/` (gitignored).

**Dependencies.** Prefer native browser/platform APIs over new third-party libraries to keep maintenance cost low, and ask before adding anything to `frontend/package.json`. Examples: drag and drop uses the native HTML5 API (`containers/DraggableContainer.tsx`, `containers/DroppableContainer.tsx`) rather than a dnd library, and localization is the `messages.json` catalog above rather than i18next/react-i18next.

## Code comments

Avoid unnecessary comments. Don't write one that's only valuable for the current session/task (e.g. narrating what you just changed, or why a past bug was fixed) — that belongs in the commit message, not the code. A comment is worth writing only when the logic isn't straightforward from reading it (a non-obvious constraint, a workaround, a "why" that isn't visible in the code itself).

## Tests

Tests live in `frontend/tests/` (not colocated): `unit/`, `integration/`, `e2e/` (Playwright: a navigation smoke test, `virtual-map-menu.spec.ts`, and `virtual-map-selection.spec.ts`, which runs the real WebGL map (selection, hover and `/map/:slug` deep links) against `page.route` stubs of the entity listing, the entity's `content_page` and block collections, and a generated glTF box, so it needs no PocketBase). Jest uses `babel-jest` + jsdom; `tests/setup.ts` polyfills `matchMedia`, `ResizeObserver`, `scrollIntoView`, `TextEncoder` and `PointerEvent` (missing from jsdom, so `fireEvent.pointerDown` would otherwise build a plain `Event` with no `button`/`clientX`; the polyfill also carries `pointerType`). `*.module.css` is mapped to a stub, and `@/mocks/*` resolves to `tests/mocks/` (e.g. `createPocketBaseMock`, `createUserRecord`, branding mocks) — prefer these over ad-hoc SDK mocks. `transformIgnorePatterns` lets babel-jest compile `three` (its `three/addons/*` files are ESM-only). jsdom has no WebGL: test scene logic against real `three` core objects (`virtual-map-scene-helper.test.ts`), and mock `createVirtualMapScene` or the `use-virtual-map` hook in hook/component tests rather than constructing a `WebGLRenderer`.

**Tests are written in English.** Every `describe`/`it` description and all test data — record names, labels, titles, slugs, file names — is en-US, even though the app's UI is pt-BR: use `label: 'Social Media'`, not `'Redes Sociais'`. Assertions on user-facing text reference the catalog (`expect(...).toHaveTextContent(messages.menuCategories.list.emptyTitle)`), never a copied pt-BR literal, so a wording change in `messages.json` can't silently break or pass a test. The only pt-BR left in `tests/` is where the language *is* the thing under test: an accented value proving a validator rejects it (`'café_a'`) and a simulated pt-BR `pb_hooks` server message.
